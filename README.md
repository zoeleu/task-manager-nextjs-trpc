# Task Manager

[Leia em português](README.pt-BR.md)

A simple task manager built with Next.js and tRPC. Tasks are kept in memory on the server and exposed through a tRPC API.

## Running it

Requires [Bun](https://bun.sh) (the repo pins `bun@1.4.4`). npm, pnpm and yarn should also work.

```bash
bun install
bun dev
```

Then open [http://localhost:3000](http://localhost:3000).

Run checks with `bun test`, `bun run lint`, and `bunx --no-install tsc --noEmit`.

For a production build: `bun run build && bun start`.

> Tasks live in memory, so they are lost whenever the server restarts.

## How it works

```
app/
  page.tsx                 Task list (server-rendered)
  tasks/[id]/page.tsx      Create (/tasks/new) and edit (/tasks/<id>) form
  api/trpc/[trpc]/route.ts tRPC HTTP endpoint
components/
  Tasks.tsx                Fetches the first page on the server
  InfiniteTasks.tsx        Loads subsequent pages on scroll
  Task.tsx                 One row: complete, edit, delete
  TaskForm.tsx             Shared create/edit form
lib/task-schema.ts         Zod schemas, shared by client and server
server/store.ts            In-memory store (a Map)
trpc/                      tRPC setup: router, context, client and server helpers
```

### tRPC API

All procedures live in `trpc/routers/_app.ts`.

| Procedure    | Type     | Input                                      | Errors                           |
| ------------ | -------- | ------------------------------------------ | -------------------------------- |
| `listTasks`  | query    | `{ limit?, cursor? }` → `{ items, nextCursor }` | `BAD_REQUEST`                 |
| `getTask`    | query    | `{ id }`                                   | `NOT_FOUND`                      |
| `createTask` | mutation | `{ title, description? }`                  | `BAD_REQUEST` (e.g. empty title) |
| `updateTask` | mutation | `{ id, title?, description?, completed? }` | `NOT_FOUND`, `BAD_REQUEST`       |
| `deleteTask` | mutation | `{ id }`                                   | `NOT_FOUND`                      |

A task has an `id` (UUIDv7, generated by the server), a `title` (1–80 chars, required), an optional `description` (up to 300 chars), `createdAt` and `completed`.

## Implementation decisions

- **The list is server-side rendered.** `components/Tasks.tsx` calls the router on the server through `caller` (no HTTP round trip) and streams in behind a `<Suspense>` spinner. The first 20 tasks seed an infinite query; an IntersectionObserver loads subsequent pages, with a manual button and retry feedback. UUIDv7 cursor pagination continues even when a boundary task is deleted.
- **One schema for client and server.** `lib/task-schema.ts` is used by tRPC to validate requests and by the form before sending, so the two can't drift apart.
- **Create and edit share one page and one form.** `/tasks/new` for creation, and `/tasks/<id>` for editing.
- **Feedback.** Validation errors appear under each form field, and server errors at the top of the form. Deleting announces success above the list. Mutations invalidate the paginated query so loaded pages stay in sync. Failed deletes and updates show an error under the task.
- **superjson** is used as the tRPC transformer, so `Date` values (like `createdAt`) survive the trip between server and client.
- **The store is kept on `globalThis`** so it isn't wiped every time the dev server hot-reloads a module.

## Notes

- **Next.js 16.** The brief mentions both Next.js 15 and "the latest versions"; this uses the latest (16.4.3).
- **English field names.** The brief names the fields `titulo`, `descricao` and `dataCriacao`; this project uses `title`, `description` and `createdAt` to keep the codebase in one language. `completed` was added to mark tasks as done.
- **Not implemented:** authentication.
